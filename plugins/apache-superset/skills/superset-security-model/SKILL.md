# Superset Security Model

## Core Concepts

### Roles and permissions (Flask-AppBuilder)
- Built-ins: `Admin` (everything), `Alpha` (all data sources, create assets, no user management), `Gamma` (consumer; sees only datasets granted via dataset access roles), `Public` (anonymous; keep empty unless public dashboards are intended), `sql_lab` (adds SQL Lab access).
- Permissions are `(permission, view/menu)` pairs plus data-access permissions `datasource access on [db].[schema].[table]`, `schema access`, `database access`. Grant data via **dataset access roles** cloned from Gamma, never by editing Gamma itself.
- `DASHBOARD_RBAC` feature flag: dashboards can be assigned to roles so Gamma users see only those dashboards (in addition to dataset access).
- `PUBLIC_ROLE_LIKE` copies permissions to Public — avoid in multi-tenant deployments.

### Row Level Security
RLS filters attach to tables and roles with a SQL clause (`tenant_id = '{tenant}'`) and type Regular (AND) or Base (applies unless role listed). Clauses can use Jinja (`{{ current_user_id() }}`, `{{ current_username() }}`) when `ENABLE_TEMPLATE_PROCESSING` is on. In embedded mode RLS can also arrive via the guest token. RLS is enforced by Superset when it generates SQL; SQL Lab bypasses dataset RLS, so SQL Lab roles must rely on engine-level policy (OPA/Trino, ClickHouse row policies).

### Keycloak / OIDC
`AUTH_TYPE = AUTH_OAUTH`, provider via `server_metadata_url` (`.well-known/openid-configuration`), PKCE with a confidential client, `AUTH_USER_REGISTRATION = True`, `AUTH_ROLES_SYNC_AT_LOGIN = True`, `AUTH_ROLES_MAPPING = {"<group>": ["<Role>"]}`, users in no mapped group are denied. Group claim from a Keycloak group mapper in the client scope; platform convention: groups `{client}_{tenant}_{role}`. Custom `SupersetSecurityManager` only to read a custom claim or implement logout; keep it small and tested. Service accounts for CI/embedding: client-credentials users mapped to a dedicated role with `can_grant_guest_token` / API permissions only.

### Hardening
- `TALISMAN_ENABLED` with CSP and `frame-ancestors` for embedding hosts; `SESSION_COOKIE_SECURE/HTTPONLY/SAMESITE`; `WTF_CSRF_ENABLED`; `ENABLE_PROXY_FIX` behind ingress.
- Database connections: `allow_dml=False`, `allow_file_upload=False`, `expose_in_sqllab` deliberate, `impersonate_user` where the engine supports it (Trino) so engine policies see the real user; credentials from Vault via `SQLALCHEMY_CUSTOM_PASSWORD_STORE` or injected env.
- Disable `ENABLE_TEMPLATE_PROCESSING` unless needed; Jinja in SQL is an injection surface.
- Public role empty; no `PUBLIC_ROLE_LIKE`; `SUPERSET_FEATURE_FLAGS` reviewed; CSV export permissions explicit.
- Audit: `ENABLE_ACCESS_REQUEST=False`; action logging to the platform audit stream (`EVENT_LOGGER`).

## Patterns
- **Role matrix generated by the control plane**: tenant roles, DAR roles and RLS rules are produced from `Tenant` + `Policy` manifests and applied via API; a nightly export compares live roles to the manifest (drift check).
- **Engine identity first**: prefer Trino impersonation + OPA so the same policy governs SQL Lab, charts and other engines; Superset RLS adds a second fence.
- **Two-tenant test**: automated test logs in as tenant A and B, lists datasets/dashboards, runs chart data; cross-tenant access must fail.

## Anti-patterns
- Granting data access by editing Gamma/Alpha
- RLS as the only isolation for SQL Lab users
- Shared service DB account across tenants with `impersonate_user=False`
- Public dashboards in a multi-tenant instance
