# Bin Pack Orderer

> Category: data ordering, bulk delivery to stores with partial commits. Batch and streaming.

## Problem

The blogging platform lets external websites embed its pages. The visits generated by these
embeddings must be exposed back to partners through an external API. The
synchronization job is shared by all partners. It builds a 10-minute processing-time window
with per-minute aggregates and then flushes the buffer to each partner's output. Events must
be delivered **individually per minute and per provider, in event-time order**.

The API ingestion storage is a streaming broker with **partial commit** semantics. A bulk request can fully succeed, fully fail, or **partially succeed**. Take
records at 10:00, 10:10 and 10:20 for one entity in one request. If only 10:20 is written, the
retry writes 10:00 and 10:10 after it, and the order is broken. Stores with this behavior:
Kinesis Data Streams `PutRecords`, DynamoDB `BatchWriteItem`, Elasticsearch bulk. The problem
is most visible in streaming, but a temporarily partial dataset at rest can also trigger
downstream processing on disordered data.

## Solution / Mechanics

Sending records one by one keeps the order but needs one request per record. The
Bin Pack Orderer keeps bulk requests and still guarantees the order:

1. **Sort** records by grouping key, then event time. A local sort per partition
   is enough when all records of an entity are in the same partition.
2. **Pack** the sorted rows into delivery bins so that **each bin holds at most one record per
   grouping key**. The n-th record of every entity goes to bin n. Bins are plain lists.
3. **Emit bins sequentially.** A retry inside a bin stays local to its group: the bin has a
   single occurrence of each key, so retrying the failed items cannot reorder anything. **The
   next bin is not delivered until the current one is fully written**.

```
 input              ORDER BY key, time        delivery bins (one record per key)
 k1 10:00           k1 09:04                   bin 1: k1 09:04 | k2 09:04 | k3 10:15
 k2 09:04           k1 10:00                   bin 2: k1 10:00 | k2 10:00
 k1 09:04   ---->   k1 10:04        ---->      bin 3: k1 10:04
 k1 10:04           k2 09:04
 k3 10:15           k2 10:00                   flush bin 1 -> retry its failures -> bin 2 -> bin 3
 k2 10:00           k3 10:15                   (3 bulk requests instead of 6)
```

The Spark + Kinesis version sorts with `sortWithinPartitions`
and, inside `foreachPartition`, resets the bin index to 0 each time `visit_id` changes.

## Consequences & trade-offs

| Consequence | What happens | Mitigation |
| --- | --- | --- |
| Retries | Ordering holds **within one execution**. If the whole pipeline fails, the retry re-emits bins that were already delivered, so the overall order breaks | Deterministic ids for idempotent sinks, consumer-side dedup, serialized runs |
| Complexity | Custom sort, bin creation and retry logic, versus calling one sort function | Keep the packer a pure function and unit test it |
| Bin count | The number of bins equals the longest per-key sequence, so one very active key creates many small trailing bins | Accept it, or cap the window size |
| API limits | A bin can exceed the request limit (Kinesis: 500 records / 5 MB) | Chunk a bin. Chunks of one bin are independent and still hold one record per key |

## Key design decisions

- **Grouping key and time column**: both must be non-null. The key is the unit of ordering
  (visit, user, device).
- **Locality**: sort per partition only if every key lives in one partition. Otherwise
  `repartition(key)` first, or two tasks race on the same key.
- **Retry policy inside a bin**: bounded attempts with backoff. On exhaustion, fail the task.
  Never skip to the next bin.
- **Target partitioning**: set the sink's partition key to the grouping key (Kinesis
  `PartitionKey`) so the sink keeps the per-key order.
- **Across runs**: serialize runs (`max_active_runs=1`, `depends_on_past=True`), and commit
  source offsets only after the last bin.

## When to use / when not

| Situation | Bin Pack Orderer? | Alternative |
| --- | --- | --- |
| Bulk API with partial commits and per-key ordering | Yes | none |
| High volume, network cost matters | Yes | none |
| Low volume, each record must go out immediately | No | FIFO Orderer |
| Sink commits bulk requests atomically (all or nothing) | Not needed | FIFO Orderer with bulk + 1 in-flight request |
| Order matters only globally, not per key | No: bins are per key | Single-threaded FIFO delivery |
| Exactly-once required across job retries | Not alone | Add idempotency patterns |

## Gotchas & troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Out-of-order records for one key in the sink | Bin holds two records of the same key, or a key is split over two partitions | Unit test the packer; repartition by key |
| Order broken after a task retry | Pipeline-level retry re-emitted bins | Deterministic `_id`, consumer dedup, idempotent sink |
| Records silently missing | Only the HTTP status was checked | Check per-item status: Kinesis `FailedRecordCount` / `ErrorCode`, ES `errors` / `items[].error` |
| Throughput no better than single writes | Parallel bins disabled and one key dominates | Expected: trailing bins are tiny; check the key distribution |
| Disorder despite bins | Bins sent from a thread pool | Bins are sequential by design |
| Kinesis `ValidationException` | Bin larger than 500 records | Chunk bins before `PutRecords` |

## Implementation notes per stack

**Spark**: `examples/bin_pack_orderer/spark/spark_bin_pack_orderer_kinesis.py`. Packer and bin delivery with retries of failed items only:

```python
for row in rows:                       # rows sorted by (visit_id, event_time)
    if key(row) != last_key:
        last_key, position = key(row), 0
    if len(bins) <= position:
        bins.append([])
    bins[position].append(row)
    position += 1
```
```python
(events.repartition("visit_id")
    .sortWithinPartitions(F.col("visit_id"), F.col("event_time"))
    .foreachPartition(write_partition(args.stream)))
```

`--self-test` checks packing and a partial-commit retry without Spark.

**Kafka**: `examples/bin_pack_orderer/kafka/kafka_bin_pack_orderer_es_sink.py`. Consume a window,
sort and pack it, send bins to Elasticsearch `_bulk`, and commit offsets after the last bin. A
deterministic `_id = visit_id-event_time` makes a replay overwrite instead of duplicate. Kafka as
a sink doesn't need the pattern: within a partition, the idempotent producer keeps order.

**Airflow**: `examples/bin_pack_orderer/airflow/bin_pack_orderer_dag.py`. Runs every 10 minutes
with one mapped task per partner. Each bin goes to `PutRecords` in chunks of 500, and failed
items are retried. Runs are serialized with `max_active_runs=1` and `depends_on_past=True`.

**Other sinks**: DynamoDB `BatchWriteItem` returns `UnprocessedItems`, so retry only those, bin
by bin. GCP Pub/Sub ordering keys need no bins (see FIFO Orderer).

## Related patterns

- **FIFO Orderer**: the simpler alternative that trades network efficiency for simplicity.
- **Local Aggregator**: the same `sortWithinPartitions` + `foreachPartition` mechanics, with no shuffle.
- **Idempotency patterns**: needed because ordering holds only within one execution.
- **Checkpointer**: commit offsets after the last bin so a restart resumes at a window boundary.
- **Compactor**: also "bin packing", but for file sizes, not ordering.
