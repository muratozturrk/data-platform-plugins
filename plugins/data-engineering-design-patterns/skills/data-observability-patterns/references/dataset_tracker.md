# Dataset Tracker

Category: Data Lineage.

## Problem
You consume a dataset of poor quality and your batch job fails regularly because one field had
different data types over time. Your direct provider is not responsible: it
processes data generated by yet another team. You need the dependencies between datasets, and
therefore between teams, to find who introduces the type inconsistency.

## Solution / Mechanics
Build a family tree of the organization's data containers (tables, folders, topics, queues),
annotated with the team that maintains each of them. The tree makes
providers and consumers explicit.

```
 [Kafka: orders_events]  (team A)
        |            \
        v             v
 [table: orders]   [table: users]   (team B)
          \           /
           v         v
     [table: orders_with_users]     (team C, you)
```

Two implementations:

**1. Fully managed**: you do nothing; the platform analyzes the jobs, tables and dashboards that
interact with each dataset. Examples: Databricks Unity Catalog lineage, GCP Dataplex for
BigQuery and Dataproc, Azure Purview. Coverage is limited to the supported jobs and stores;
for example, Dataplex records lineage for BigQuery load jobs but not for the BigQuery Data
Transfer Service.

**2. Custom**: you implement lineage yourself.
1. Identify inputs and outputs of each query, task or pipeline, at one of two levels:
   - *orchestration layer*: each pipeline declares its inputs and outputs and reports them to
     a lineage service; some tools detect them automatically (Airflow + OpenLineage);
   - *database layer*: a lineage job analyzes the executed queries, turns each query into a
     tree and extracts the referenced tables
     (`SELECT ... FROM orders o JOIN users u ON u.id = o.user_id` gives orders, users).
2. Store the dependencies in a lineage service.
3. Add a layer that interprets and visualizes them.

```
 jobs / queries --(inputs, outputs)--> extraction (orchestrator hooks | query-log parser)
                                              |
                                              v  RunEvents (START/COMPLETE/FAIL)
                                      lineage service (OpenLineage API -> Marquez)
                                              |
                                              v
                                      graph UI / API  -> "who produces my input?"
```

The managed approach follows the same flow; only the extraction is out of the box.

## Consequences & trade-offs
- **Vendor lock**: managed solutions work within the service scope. With open
  source stores or databases in other clouds you get only a partial view of the lineage.
- **Custom work**: orchestrators deduce inputs and outputs from built-in task
  configurations. Custom task types need their own input/output resolution logic, otherwise
  they are invisible in the graph.
- The custom approach is flexible but costs implementation and operation effort: more
  deployed services to monitor and more interactions between them.

## Key design decisions

| Decision | Options | Notes |
|----------|---------|-------|
| Implementation | managed (Unity Catalog, Dataplex, Purview), custom (OpenLineage + Marquez) | managed if everything runs in one platform |
| Extraction level | orchestration (task inlets/outlets), database (query logs), job runtime (Spark listener) | combine them; each covers different jobs |
| Naming | namespace per system (`kafka://host`, `postgres://host`) and per team | consistent names are what join events from different tools |
| Ownership | team in namespace, job facet or catalog tags | required to answer "which team?" |
| Granularity | dataset only, or dataset + column | column level is the Fine-Grained Tracker |

**When to use / when not to use**

| Use it when | Do not use it when | Alternative |
|-------------|--------------------|-------------|
| Many teams exchange datasets and ownership is unclear | One small team owns a handful of pipelines | a README / data catalog page per dataset |
| You need impact analysis before schema changes | You need to know which input column builds an output column | Fine-Grained Tracker |
| Upstream issues must be routed to the right team | You need to know which job version wrote a given row | Fine-Grained Tracker (row level) |

## Gotchas & best practices
- Use the same dataset name in every emitter. A topic named `visits` by Spark and
  `kafka://broker:9092/visits` by a custom emitter shows up as two nodes.
- Emit FAIL events too. A graph with only successful runs hides who stopped producing.
- Custom Python tasks in Airflow need explicit `inlets`/`outlets`; otherwise only SQL operators
  appear.
- Short-lived Spark jobs must stop the session cleanly (`spark.stop()`), or the last
  COMPLETE event may not be sent.
- Pin the OpenLineage Spark agent to the Scala version of the cluster (`_2.12` vs `_2.13`).
- Treat the lineage backend as production infrastructure: if it is down, events are lost
  unless the transport buffers them.

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| Spark job visible, but no input datasets | unsupported source format or missing agent jar | check the agent version and the supported sources list |
| Same topic appears twice | different namespaces/names across tools | agree on a naming convention |
| Python task missing from the graph | opaque custom task | declare inlets/outlets or emit events manually |
| Graph stops at a cloud boundary | managed lineage scope | add OpenLineage emitters on the other side |
| No events from Airflow | provider not installed or transport not configured | `apache-airflow-providers-openlineage` + `AIRFLOW__OPENLINEAGE__TRANSPORT` |

## Implementation notes per stack
**Spark** - `examples/dataset_tracker/spark/openlineage_spark_job.py`:

```python
SparkSession.builder.appName(app_name)
    .config("spark.extraListeners", "io.openlineage.spark.agent.OpenLineageSparkListener")
    .config("spark.openlineage.transport.type", "http")
    .config("spark.openlineage.transport.url", os.environ.get("OPENLINEAGE_URL", "http://localhost:5000"))
    .config("spark.openlineage.namespace", os.environ.get("OPENLINEAGE_NAMESPACE", "orders_team"))
    .config("spark.jars.packages", "io.openlineage:openlineage-spark_2.12:1.21.1")
```
The join `orders + users -> orders_with_users` then appears in Marquez.

**Airflow** - `examples/dataset_tracker/airflow/openlineage_dag.py`: with
`apache-airflow-providers-openlineage` installed and `OPENLINEAGE_URL` (or the transport
setting) configured, SQL operators are extracted automatically. The
custom task declares its datasets:

```python
@task(inlets=[Table(cluster=CLUSTER, database="dp", name="orders_with_users")],
      outlets=[Table(cluster="s3://exports", database="exports", name="orders_with_users_csv")])
def export_to_partner() -> None: ...
```

**Kafka** - `examples/dataset_tracker/kafka/manual_lineage_emitter.py`: plain clients have no
integration, so the job emits its own START / COMPLETE / FAIL `RunEvent`s with `kafka://`
datasets through `openlineage-python` (the manual flow).
